# Field Guard — Welthungerhilfe

Dashboard for a Welthungerhilfe extension officer (Felix) who advises ~20 farmers on crop
disease and farm visits: login, today's priorities (schedule + route map) and a farm profile
(sensor KPIs, AI finding, farmer's report, steps to take).

## Run

Requires Node.js 18+.

```bash
npm install
npm run dev      # http://localhost:5173 — /api is proxied to the Functions host (vite.config.js)
```

Demo login: `felix` / `demo` (mock, see `src/auth/officer.js`).

## Live backend data

`src/api/client.js` calls the Azure Function App (`/api`, same origin in production).

| Screen | Endpoint | What becomes live |
|---|---|---|
| Dashboard | `GET /api/risk` (polled 20 s) | visit type (green → regular check, yellow/red → disease warning), summary |
| Farm profile | `GET /api/farms/{fieldId}` (polled 10 s) | sensor tiles + 7-day history, update time, risk level (AI colour), finding (AI reasoning + out-of-range sensors), farmer call, steps |
| Live sensor view (click the sensor tiles) | `GET /api/readings?deviceId=…` (polled 5 s) | 4 time series of the last 120 readings; Azure architecture from `azure/terraform` with each new reading, poll, LED colour and scoring run animated |

Only farms mapped in `src/data/farmFieldMap.js` are live: `f01` Hillside Farm → `field-a` →
`box-01` (the real Arduino), `f04` Mango Grove → `field-b` → `box-02` (red late-blight showcase),
and `f14` Valley View → `field-d` → `box-03` (yellow, medium risk). Every other farm, and every
farm while the backend is unreachable, shows the demo data from `src/data/`. The farm profile
labels the sensor block "Live" or "Demo data". The risk finding, steps, alerts and farmer call for
the live farms are all generated by the Azure model at scoring time — only the raw readings are
synthetic (seeded via `azure/functionapp/seed_telemetry.py` / `azure/scripts/replay_blight_nights.py`).

`box-01` is a real Arduino: its readings drive `f01` (the demo hero) live, so physically changing
the sensor (e.g. pouring water on it) moves the live sensor view within ~5 s and the farm's sensor
tiles within ~10 s. `box-02` and `box-03` are demo-seeded; replay exact blight-night counts with
`python3 azure/scripts/replay_blight_nights.py --device box-02 --nights 4` (f04 red) and
`--device box-03 --nights 2` (f14 yellow).

```
  data/farmFieldMap.js     which demo farms are backed by a real backend field/device

  data/sensorMetrics.js    live-reading metric model + thresholds (mirror azure/functionapp/views.py)
  data/farms.js            20 assigned farms (mock) + map positions
  data/todayPlan.js        today's visits in route order: type, duration, drive time/km, finding, advice focus
  data/schedule.js         builds the 08:00–16:00 day (drives + visits); RAINY_SEASON doubles drive times
  data/visitTypes.js       regular check / sensor disease warning / farmer asked for help
  utils/                   greeting, time formatting, emphasis (**bold** markup)
  auth/officer.js          mock officer profile + sign-in
  pages/LoginPage.jsx      login screen
  pages/Dashboard.jsx      Hoang's priorities for today (calendar + route map), live risk overlay
  pages/FarmProfile.jsx    farm profile: owner card, risk (sensor data vs. farmer's report), steps to take
```

## Field assumptions

- Visit ~60 min (45–90), drive ~30 min (20–45, double in rainy season), 3–5 visits per day max.
- 20 farms on a 2-week cycle need 2 regular visits a day; remaining slots go to farms that need action.
- Farms that need action (sensor disease warning or farmer asked for help) are red; regular checks green.

## Design rules carried over from the WHH site

- Green `#2FAB16` for brand and every action; red is reserved for donations on the WHH site, so it is not used here.
- Square cards, inputs and tags; pill-shaped buttons.
- White / light grey / green bands, with white cards overlapping the band edge.
- Headline font: Core Sans WHH (licensed). Stand-ins: Barlow Condensed + Nunito Sans (Google Fonts).
